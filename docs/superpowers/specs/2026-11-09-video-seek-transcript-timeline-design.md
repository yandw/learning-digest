# 视频拖拽后的逐字稿时间轴排序设计

日期：2026-11-09
状态：产品规则已确认，等待实施计划
涉及版本：0.1.53 → 0.1.54

## 1. 背景

Learning Digest 当前会按固定长度采集课程音频并生成带视频时间戳的逐字稿。用户拖拽视频播放点后，新的转写结果可能晚于旧区间返回。例如：

1. 0–20 已转写；
2. 拖到 40，20–40 被标记为“已跳过”，40–45 完成转写；
3. 再拖回 30，30–40 会被补转。

如果逐字稿只按识别结果到达的先后顺序排列，最终顺序会变成 `0–20 → 40–45 → 30–40`，而不是正确的视频时间轴顺序。当前侧边栏也是按到达顺序追加显示，Topic 摘要和最终学习纪要的输入同样直接消费这份原始顺序。

此外，当前向前拖拽的判断依赖“一个录音块长度加 5 秒”。默认录音块为 30 秒时，小于该长度的拖拽可能仍被当成连续播放，导致拖拽前后的两段不相邻声音被拼进同一个识别块。

## 2. 已确认的产品规则

以下规则已经和需求方确认：

1. 正常播放时，按视频时间持续识别并增加逐字稿。
2. 向前拖拽时：
   - 提交拖拽前已经录到的内容；
   - 中间没有播放的区间标记为“已跳过”；
   - 从实际落点继续识别。
3. 向前位置一次增加超过 **3 秒**，判定为用户拖拽了播放点。
4. 播放位置向后变化，判定为用户倒回播放点。
5. 倒回尚未转写的区间时，从实际落点开始补转。
6. 原来的“已跳过 20–40”在补转 30–40 成功后，应显示为“已跳过 20–30”。
7. 倒回已经转写成功的区间时：
   - 不重新调用语音识别；
   - 保留原有文字；
   - 直接推进到下一个尚未处理的采集点。
8. 倒回识别失败的区间时，允许重新识别；成功后替换失败提示。
9. 默认“录一段、识别一段”和“百炼实时识别”两种方式都要遵守同一套规则。
10. 所有面向用户和 AI 的逐字稿顺序，都按照视频播放时间排序，而不是按照识别结果返回顺序排序。
11. 一段视频已经播放并采集过，即使没有识别出文字，也要视为已经处理，不能因为静音而误判为未处理。

目标时间轴示例：

```text
0–20      已识别
20–30     已跳过
30–40     后补识别
40–45     已识别
45以后    继续识别
```

## 3. 目标与非目标

### 3.1 目标

- 拖拽后的音频绝不允许跨过拖拽点拼接。
- 倒回空洞时可以补转，并能把结果插入正确的时间位置。
- 已经识别成功的区间不会被重复识别或重复计费。
- 识别失败的区间仍然可以补转。
- 侧边栏、Topic 输入、最终学习纪要都使用统一的视频时间轴顺序。
- 分段识别和实时识别共享同一套时间轴判断结果。

### 3.2 非目标

- 本设计不新增课程平台适配器。
- 本设计不改变 Topic 的“只追加、不回头重写”策略。
- 本设计不纠正非 1 倍播放速度导致的墙钟与视频时间偏差；现有偏差继续按已知限制处理。
- 纯墙钟直播 Session 不启用视频拖拽重排；它仍按发生顺序处理。已经对齐到视频时间轴的 Session 使用本设计。

## 4. 总体设计

### 4.1 新增统一时间轴模块

新增纯逻辑模块 `session-timeline.js`，在 Node 测试和浏览器环境中复用。它不替代现有 Session 状态机，而是把原始状态整理成统一的时间轴视图。

模块至少提供三类结果：

1. **有序逐字稿**
   - 按记录的视频 `start` 升序排列；
   - `start` 相同时按原始到达顺序稳定排列；
   - 空洞标记、失败标记和普通文字都参与同一排序结果。

2. **时间轴覆盖状态**
   - 转写成功的 Segment 视为已覆盖，即使该 Segment 没有识别出文字；
   - 实时识别产生正常逐字稿记录后，对应区间视为已覆盖；
   - 实时模式下单独记录已经播放并采集过的视频区间，用来覆盖“只有静音、没有文字”的部分；
   - 失败 Segment 和失败实时识别保留为可补转状态；
   - “已跳过”标记保留为空洞，允许用户倒回补转。

3. **下一个采集点**
   - 输入当前视频位置和时间轴状态；
   - 跳过已经覆盖的区间；
   - 返回下一个空洞、失败区间或全新内容位置；
   - 如果没有需要采集的位置，则明确返回“继续等待”。

原始 `transcriptRecords` 和 `segments` 仍按事件到达顺序持久化。现有 Session 快照不需要迁移，旧数据可直接由时间轴模块重新计算有序结果。

### 4.2 拖拽识别

页面桥接层继续每秒上报视频位置。

- 正常播放时，位置大约每秒增加 1 秒。
- 当前位置比上一次位置增加超过 3 秒，判定为向前拖拽。
- 当前位置比上一次位置小，判定为倒回。
- 一旦判定为拖拽，拖拽前后的音频必须在落点切开，不允许继续合并成同一个识别块。

页面桥接层除每秒轮询外，还监听主视频元素的拖拽事件并立即上报当前位置。轮询继续保留，作为事件丢失时的兜底；即时上报用于尽量缩短“真实拖拽发生”和“扩展开始处理”之间的时间，减少落点前后的音频归属误差。

该规则替代当前“一个 Segment 长度加 5 秒”的向前拖拽判断。

## 5. 分段识别模式

### 5.1 向前拖拽

从 20 分钟拖到 40 分钟时：

1. 提交拖拽前已经采集且属于 20 分钟之前的内容；
2. 将 20–40 记录为“已跳过”；
3. 从 40 分钟建立新的采集位置；
4. 后续识别结果使用 40 分钟之后的时间。

### 5.2 倒回空洞

从 45 分钟倒回 30 分钟，且 20–40 是尚未转写的空洞时：

1. 丢弃倒回前缓冲里不属于 30 分钟之后的内容；
2. 从实际落点 30 分钟开始补转；
3. 补转成功后，把“已跳过 20–40”缩小为“已跳过 20–30”；
4. 新结果按 30–40 的时间插入逐字稿。

### 5.3 倒回已覆盖区间

如果倒回点位于已经识别成功的区间：

- 不重发这部分音频；
- 保留原来的识别结果；
- 播放推进到下一个空洞、失败区间或全新内容时，再从那里继续采集。

例如从 42 分钟倒回，而已覆盖区间是 40–45：

- 42–45 不重复识别；
- 到达 45 后，从 45 继续识别新内容。

### 5.4 补转失败

补转 Segment 提交后，只有识别成功才缩小对应空洞。

- 成功：用实际文字替换补转区间；
- 失败：保留原“已跳过”标记，并显示本次补转失败；
- 不允许失败后把空洞错误地标记成已覆盖；
- 异步结果无论多晚返回，都必须绑定它原本对应的视频区间，而不是绑定当前播放位置。

## 6. 实时识别模式

实时识别不能直接把倒回后的声音接到原识别连接后面，因为识别服务只会按声音实际到达的顺序理解内容。因此实时模式采用“重设识别起点”的方式处理拖拽。

### 6.1 拖拽发生

检测到有效拖拽后：

1. 先结束当前识别连接中尚未完成的半句，确保已收到的声音被完整提交；
2. 关闭旧识别连接；
3. 根据落点和时间轴覆盖状态决定下一步；
4. 需要采集时，从对应视频位置建立新的识别连接。

### 6.2 向前拖到新区间

例如拖到 40 分钟：

- 40 分钟之前已经完成提交的内容保留；
- 中间没有播放的内容记录为“已跳过”；
- 新连接明确从 40 分钟开始计算识别时间。

### 6.3 倒回空洞或失败区间

例如倒回 30 分钟：

- 新连接从 30 分钟开始；
- 30–40 的识别结果按视频时间插入；
- 成功后缩小对应“已跳过”范围；
- 失败后保留原空洞或失败状态。

### 6.4 倒回已覆盖区间

倒回已经识别成功的区间时，不把这期间的重复声音继续发给识别服务。

- 只跟踪视频位置；
- 播放推进到下一个需要采集的位置后，再从该位置恢复上送音频；
- 不重复计费，也不生成重复逐字稿。

### 6.5 连接重试与失败

- 非用户拖拽引起的网络断开，沿用现有自动重连规则，不改变识别时间原点。
- 拖拽后的重设过程如果最终失败：
  - 保留已经得到的逐字稿；
  - 明确向用户提示实时识别无法继续；
  - 不允许在不知道当前视频起点的情况下继续生成看似正常的时间戳。

## 7. 数据与持久化

### 7.1 Session 状态

- 现有 `segments`、`transcriptRecords`、`topics` 的结构不改变。
- 原始记录仍按事件到达顺序保存。
- 有序结果由时间轴模块计算，不把排序结果重复持久化。
- 旧 Session 快照无需迁移。

### 7.2 活动采集上下文

实时识别需要额外保存当前识别起点和已经播放采集过的视频区间，用于：

- 服务 Worker 重启后的恢复；
- 判断倒回区间是否已经覆盖；
- 区分“静音但已处理”和“尚未处理”。

这些新增字段保存在现有活动采集指针中，属于新增的活动上下文信息，不改变历史 Session 快照。

## 8. 展示与 AI 输入

### 8.1 侧边栏逐字稿

侧边栏不再简单地把每条结果追加到底部，而是按照视频时间同步页面内容：

- 30–40 的晚到结果插入到 40–45 前面；
- 已存在的 40–45 行不被删除或重复创建；
- “已跳过 20–40”原地更新为“已跳过 20–30”；
- 搜索、时间跳转和阅读位置状态继续可用。

### 8.2 AI 输入

以下入口统一使用有序逐字稿：

- 学习过程中的 Topic 摘要输入；
- Session 结束时的一次完整学习纪要输入；
- 其他依赖逐字稿上下文的功能。

AI 输入中不再出现晚到的 30–40 内容排在 40–45 后面的情况。

## 9. 错误处理

1. **异步结果乱序**：结果始终绑定原始采集区间，再由时间轴模块排序。
2. **补转失败**：保留原空洞或失败状态，不缩小已跳过范围。
3. **重复倒回**：同一个已成功区间不会因为多次倒回而重复识别。
4. **倒回途中再次拖拽**：丢弃未落定的缓冲，按新落点重新计算。
5. **Worker 重启**：从持久化快照和活动采集上下文恢复，已完成区间不重复识别。
6. **实时重设失败**：保留现有内容，明确提示，并停止生成不可靠的新时间戳。

## 10. 测试要求

新增测试至少覆盖：

### 时间轴模块

- 按视频时间排序；
- 相同起始时间的稳定排序；
- 成功 Segment 的覆盖判断；
- 无文字 Segment 的覆盖判断；
- 失败区间和跳过空洞的区分；
- 下一个采集点计算；
- 旧快照结构兼容。

### 分段识别

- 向前超过 3 秒判定为拖拽；
- 拖拽点前后音频不合并；
- 20–40 空洞缩小为 20–30；
- 30–40 晚到结果插入正确位置；
- 40–45 已覆盖区间不重复识别；
- 到达 45 后继续识别；
- 补转失败不吞掉原空洞。

### 实时识别

- 向前拖拽后重新从落点开始；
- 倒回空洞后从实际落点补转；
- 倒回已覆盖区间时不重复上送；
- 推进到新采集点后恢复；
- 重设识别起点的时间戳绑定正确。

### UI 与 AI 输入

- 侧边栏按视频时间插入、更新和删除对应行；
- 空洞标记原地更新；
- Topic 输入有序；
- 最终学习纪要输入有序。

### 发布检查

- 新模块进入发布白名单；
- `manifest.json`、`package.json` 和发布测试中的版本同步提升到 0.1.54；
- 全部 Node 测试和 `npm run check` 通过。

## 11. 成功标准

- 用户描述的多轮拖拽和补转场景可以得到正确时间轴；
- 已识别内容不重复采集、不重复计费；
- 跳过、失败和成功补转状态准确；
- 侧边栏、Topic 摘要和最终纪要顺序一致；
- 分段识别与实时识别遵守同一产品规则；
- 新测试和现有测试全部通过。
